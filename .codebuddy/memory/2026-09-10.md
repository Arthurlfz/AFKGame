## ✅ 服务端会话表 + 真互踢（登录会话第二批）
- 新增 `supabase/migrate_user_sessions.sql`（**已 apply 到线上库**，`supabase_apply_migration` 名 `user_sessions_login_mutex`）：`user_sessions` 表（session_id 由客户端生成、localStorage 持久化、同浏览器多标签共用）+ 3 个 RPC（`session_login` / `session_heartbeat` / `session_logout`）+ RLS(select own) + 加入 `supabase_realtime` publication。
- ⭐ **语义关键：login 与 resume 必须分开**。`p_kick_others=true`（真登录/新设备首次打开）撤销其他设备；`false`（页面刷新恢复）只激活自己、被撤销就如实报告 —— **绝不复活**，否则两台设备会"谁刷新谁赢"来回互踢。
- 客户端新增 `docs/js/core/server-session.js`：`bootstrap()`（localStorage 有 id = 恢复不抢；没有 = 新设备抢）+ 45 秒心跳（兼做"挂着机被封禁"的实时复查）+ Realtime 订阅 `user_sessions` 自己那行（秒级踢人，心跳只是兜底）+ `conflict`（session_id 撞车）自动换 id 重试一次。**网络异常 / RPC 报错一律不踢人**，只有服务端明确说 revoked / banned 才动。
- 未登记 id 的两道闸（都返回 `unregistered`）：① `session_heartbeat` 仅当该账号无其他活跃会话时才自动登记；② `session_login(kick=false)` 遇到"本地有 id、服务端从没登记过"且账号已有活跃会话时一律拒绝。**缺了 ② 就等于"清掉 localStorage 换个新 id 刷新一下"就绕过互踢**（新会话被激活、老会话还活着）—— 这是自检时发现的漏洞，已补并实测（第 7 步 unregistered / 第 8 步真登录才允许接管）。
- 服务端逻辑用**事务 + 模拟 JWT** 实测 9 步全对（A登录→B登录顶掉A→A恢复报 revoked→未知 id unregistered→封禁心跳 banned→封禁登录 banned→logout）。

- 🔴 **测试抓到的真 bug**：`reportKick` 里 `reason` 装的是封禁原因文案（如"开挂"），而 main.js 用 `reason === 'banned'` 判断封禁 → 封禁会被显示成"其他设备登录"。已改成 payload 带 `banned` 布尔，main.js 按布尔判断。**教训：事件 payload 里"状态"和"原因文案"必须分开，别拿文案做判断。**
