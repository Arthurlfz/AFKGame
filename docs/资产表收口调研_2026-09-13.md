## 一、先澄清一个容易被误判的事实

**这三张表的 RLS 是开着的**（配置在 Supabase 后台，所以仓库里搜不到），实测用未登录的 key 去读：

```
pets         → []
equip_items  → []
pet_egg      → []
materials    → []
```

所以现状**不是**「任何人能看到/改所有人的数据」。

真正的风险面只有一条：**登录玩家可以绕过游戏，直接用 REST 改「自己那一行」的任意列任意值。**

> ⚠️ 仓库里查不到 RLS 策略 ≠ 线上没配。**这类表是在 Dashboard 建的，配置从来没落到 SQL 文件里。**
> 想知道真实状态就用 `select relname, relrowsecurity from pg_class where relname in (...)`，别只 grep 仓库。

## 四、⚠️ 为什么 CHECK 约束（软护栏）不等于安全

这是本次调研最该记住的一点：

加一条 `check (level between 1 and 60)` 之后——

```
PATCH {"level": 99999}  →  被拦下 ✅
PATCH {"level": 60}     →  照样通过 ❌   ← 因为 60 本身是合法值
```

**约束只能拦住越界的写法，拦不住"直接改成合法上限"。**

真正的防线是**服务端知道这只宠本该是多少级** —— 也就是必须有服务端的真值源。
所以这条路绕了一圈还是回到 #1。

同理，给 `equip_items.affixes` 加 jsonb schema 校验也只能保证"格式合法"，
保证不了"这件极品词缀是你打出来的而不是你自己敲出来的"。

## 五、单点风险（会比其它问题更早出事）

### 🔴 `pets.equipment` jsonb 无归属校验

`pets.equipment` 存的是 `{部位: 装备id}`，**目前没有任何校验** ——
玩家可以直接把**别人的装备 id** 填进自己的装备槽。

这跟"改自己的等级"性质不同：**这是直接侵害他人的资产。**

修复方向：触发器校验槽位里的每个 id 都属于同一 `user_id`。

⚠️ **但有个坑要提前想清楚**：`buy_pet` RPC 会 `update pets set user_id`（换主人），
如果触发器写成 `before update`（不限定列），**买宠会当场挂掉**。
必须写成 `before insert or update of equipment`，并且想清楚
「买来的宠物如果原本带着装备，那些 id 归属谁」这个业务规则。

## 六、现有约束盘点（加新约束前必看）

| 表 | 已有 CHECK | 触发器 |
|---|---|---|
| `pets` | `pets_growth_ck check (growth between 1 and 100)`（`migrate_god_pet.sql:22`） | 无 |
| `pets.level` | **完全没有约束**（`Config.pet.maxLevel=60` 从未落到数据库） | — |
| `equip_items` | 无 | 无 |
| `pet_egg` | `check (status in ('未孵化','已孵化'))` | 无 |

关键取值（从 `config.js` 核实，别猜）：
- `equip_items.rarity` = **`white` / `blue` / `gold`**（`config.js:1250`，不是"白/蓝/金"）
- `equip_items.tier` = **1~5**（`config.js:952`）
- `pets.growth` 上限 100、`pets.level` 上限 60

> 🔴 加约束时务必用 **`not valid`**：Postgres 加约束会全表扫描校验历史数据，
> 只要有一行不合规就整体失败。**别让一条运维操作把游戏写挂。**
