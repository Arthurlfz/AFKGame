## 一、要解决什么

现在**玩家挂出去的东西，只有"别的在线玩家"的机器人会来买**。

- 机器人跑在每个玩家的浏览器里（`market_bot.js` 的 `start()` 由 main.js 调起，靠页面里 `setInterval`/`setTimeout`）
- 且它**不买自己挂的单**（`market_bot.js:376` 过滤 `seller_id === user.id`，防"自挂自买刷材料"）
- 结果：**一个人玩 = 挂出去永远没人买**；人少的时候，市场就是死的

游戏对外主打的是「你打到的东西能卖给真实的玩家」，**这句话目前兑现不了**。新人挂一件白装上去，等一天也没人来，只会觉得这功能是摆设。

不做会怎样：**卖点落空 + 新人前十分钟流失 + 老玩家没有出货口**。

## 五、经济账（2026-09-13 粗算，量级用，不是精算）

> ⚠️ **没有真实玩家数据，以下都是量级估算，用来定"保守起步值"，不是最终值。**

**产出端**（config.js 注释的实测口径，2026-08-31）：
| 项 | 每小时 | 每天（24h 满负荷挂机） |
|---|---|---|
| 战斗场次 | ~700 场 | ~16800 场 |
| 装备 | 7.7 ~ 10.4 件 | ~240 件 |
| 材料 | ~59 件 | ~1400 件 |
| 宠物蛋 | ~4.2 个 | ~100 个 |

**注入端**（机器人收购 = 给卖家材料 + 销毁装备）：
- 现有出价上限（`config.js:1323` `marketBot.prices`）：白装 2~6、蓝装 4~10、金装 8~20 个材料
- 取**每件平均注入 ~5 个材料**

**风险测算**：
| 每日收购件数 | 每日注入材料 | 相当于几个玩家满负荷产出 |
|---|---|---|
| 1330 件（现有 65 秒/次不设限，24h 不停） | ~6600 | **≈ 4.7 个玩家** |
| 100 件 | ~500 | ≈ 0.36 个玩家 |
| **30 件（建议起步值）** | **~150** | **≈ 0.1 个玩家** |

**结论：不设限必然通胀**（注入量是单个玩家产出的近 5 倍，玩家越多越失衡）。

### 🔴 建议的保守起步参数（用户 2026-09-13 拍板「保守」）

| 参数 | 建议值 | 理由 |
|---|---|---|
| 每日全局收购上限 | **30 件** | 注入 ≈ 单玩家产出的 10%；宁可玩家偶尔卖不掉，也不让材料贬值 |
| 收货价位 | 标价 ≤ 参考价上限 × **0.6** | 比现有「≤ 上限」更严（现有 `isCheap` 是 ≤ 上限） |
| 收货稀有度 | **只收白 / 蓝**，不收金装 | 金装是玩家的宝贝，留给真人交易才有意思 |
| 收购后处理 | 沿用现有 **80% 销毁**（sink） | 别改，动着就是新的经济变量 |
| 扫描间隔 | 由每日上限反推，不必卡秒 | 上限才是闸门，间隔只是节奏 |

### ❗ 这笔账现在算不准的原因（别假装算出来了）

**缺消耗端数据**：玩家一天在打造 / 进化 / 涅槃上**吃掉多少材料**，没有数。
- 如果消耗远大于产出，机器人多注入一点其实是**健康的**（否则玩家根本没材料打造）
- 如果消耗小于产出，注入 10% 都可能太多

**所以正确做法不是一次算准，而是**：
1. 先用上面的**保守值**上线
2. 加一个可观测指标：**每天机器人注入了多少材料**（服务端记一笔就行）
3. 跑一段时间看真实数据，再调上限

## 五之二、调参速查（改完 1 分钟内对在线玩家生效，不用重启、不用刷页面）

```sql
-- 只改某几个参数（其余保留）
update public.game_config_overrides
   set config = jsonb_set(config, '{bot}', coalesce(config->'bot','{}'::jsonb) || '{"dailyCap": 60}'::jsonb),
       updated_at = now()
 where id = true;

-- 一次设全
update public.game_config_overrides
   set config = jsonb_set(config, '{bot}',
         '{"enabled":true,"dailyCap":30,"materialDailyCap":20,"maxPrice":10}'::jsonb),
       updated_at = now()
 where id = true;

-- 临时全关（前端机器人也会一起停）
update public.game_config_overrides
   set config = jsonb_set(config, '{bot,enabled}', 'false'::jsonb), updated_at = now()
 where id = true;
```

| 参数 | 作用 | 调大的代价 |
|---|---|---|
| `dailyCap` | 每天最多收几件**装备** | 装备更好卖，但材料注入变多 → 逼近通胀 |
| `materialDailyCap` | 每天最多收几笔**材料**（独立配额） | 同上 |
| `maxPrice` | 只收标价 ≤ 这个数 | 贵的也能卖掉，但机器人变成"兜底收购站"，真人交易被架空 |

⚠️ **调之前先看**：`select coalesce(kind,'equip'), count(*), sum(net_qty) from market_bot_sweep_log
where created_at >= date_trunc('day', now()) group by 1;`

> 📌 **为什么不做进开发者面板**（我的技术判断，供你反驳）：面板的调参体系是"改内存 Config + 存整份快照"，
> 而机器人参数住在另一个 jsonb 里、且两者保存会互相覆盖。为了 3 个低频参数去改渲染体系，风险和收益不成比例。
> 调参是低频动作（一周几次），复制一条 SQL 的成本可接受。**等你觉得烦了，我们再花半天做进面板。**
