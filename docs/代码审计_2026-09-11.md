**范围**：`docs/js/`（72 文件 / 约 1.5MB）+ `supabase/*.sql`（25 个）+ `supabase/functions/`。

## 🔴 P0-1　`bot_buy_material` 从诞生起就没有任何守卫 —— 可无限把材料 A 换成材料 B

### 文档说应该是这样
- `PROJECT_CONSTITUTION.md` B10 两条红线：**"消耗端必须存在（sink）"、"AI 只买不高于价值模型上限的单"**。
- `docs/js/core/config.js:1358` 定义了守卫参数：`minAccountAgeSec: 600`（新号 10 分钟静默期）、`dailyCap: 30`（每天 30 次）。
- `docs/js/core/market_bot.js:37` 注释明说"服务端会拒：未登录 / 封禁 / 新号不满10分钟 / 每日上限"。

### 代码实际是这样
`supabase/migrate_material_listings.sql:177-214`（提交于 **2026-09-10**）：

```sql
create or replace function public.bot_buy_material(p_listing_id uuid)
...
begin
  select * into v_listing from public.material_listings
  where id = p_listing_id and status = 'active' for update;
  if not found then return 'notfound'; end if;

  -- 直接给卖家发材料，没有任何前置校验
  insert into public.materials (user_id, name, quantity)
  values (v_listing.seller_id, v_listing.material_type, v_net) ...

  update public.material_listings set status = 'sold' where id = p_listing_id;
```

对照 `supabase/migrate_security_hardening.sql:149-194`（09-03 写的 equip 版），**缺 3 个强制点**：

| 强制点 | equip 版 | material 版 |
|---|---|---|
| `perform public.bot_buy_guard();`（身份/封禁/账号年龄/每日30次） | ✅ 有 | ❌ **无** |
| `if v_listing.seller_id::text = auth.uid()::text then return 'self'` | ✅ 有 | ❌ **无** |
| `grant execute ... to authenticated`（不是 anon） | ✅ | ❌ **第 214 行 `to anon, authenticated`** |

`migrate_security_hardening.sql` 里**根本没有 `bot_buy_material`**（已核对，出现 0 次）——因为它 09-10 才出生，而 hardening 是 09-03 的。所以 hardening 末尾"统一收 anon 权限"那一刀**从来没覆盖过它**。

### 攻击 / 受害
- **攻击者**：任何登录玩家（甚至未登录，因为 grant 给了 anon）。不需要改前端，DevTools 里一行就行：
  ```js
  supabase.rpc('bot_buy_material', { p_listing_id: '自己挂的单' })
  ```
- **路径**：`list_material` 扣掉自己 `good_qty` 个甲材料（`migrate_material_listings.sql:73`）→ 立刻 `bot_buy_material` 自己的单 → 系统凭空发 `material_type` 的乙材料，标记 sold。
- **因为缺 self 校验**，不用找人接手，**自己挂自己买**，可以无限循环。
- **受害者**：整个材料经济。稀缺材料（涅槃丹/强化丹/锁定石/凝魂晶石）可以用垃圾材料无限兑换。`dailyCap=30` 这条唯一的刹车完全不在。

### 修复（最小改动）
在 `bot_buy_material` 的 `begin` 后补三行，和 equip 版对齐：

```sql
begin
  perform public.bot_buy_guard();

  select * into v_listing from public.material_listings
  where id = p_listing_id and status = 'active' for update;
  if not found then return 'notfound'; end if;

  if v_listing.seller_id::text = auth.uid()::text then return 'self'; end if;
```

末尾加：
```sql
insert into public.security_bot_buy_log (user_id, listing_id, kind)
values (auth.uid(), p_listing_id, 'material');
revoke execute on function public.bot_buy_material(uuid) from anon;
```
`kind` 列的 check 约束目前是 `check (kind in ('pet','equip'))`，加 `'material'` 要同步改（`migrate_security_hardening.sql:101`）。

## 🔴 P0-2　"幂等、可重复跑"是假的 —— 重放旧脚本会静默抹掉安全加固

### 文档说应该是这样
`PROJECT_CONSTITUTION.md:18` 和 `skill: forge-of-souls-dev` 都写：**`supabase/migrate_*.sql`（幂等，可重复跑）**。

### 代码实际是这样
同一个函数被**多个文件重复 `create or replace`**，谁后跑谁生效：

| 函数 | 定义在几个文件 | 最新一份是否带守卫 |
|---|---|---|
| `bot_buy_equip` | `migrate_bot_buy.sql` / `migrate_security_hardening.sql` / **`migrate_trade_records_ref.sql`（09-10）** | ❌ 不带 |
| `bot_buy_pet` | 同上 3 个 | ❌ 不带 |
| `buy_equip` / `buy_pet` | `migrate_material_trade.sql` / **`migrate_trade_records_ref.sql`（09-10）** | — |
| `buy_egg` | `migrate_egg_species_trade.sql` / **`migrate_trade_records_ref.sql`（09-10）** | — |
| `battle_settle` | `migrate_idle_sessions.sql` / `migrate_battle_pending_script.sql` | — |

具体退化（已逐行比对 `migrate_security_hardening.sql:149-194` vs `migrate_trade_records_ref.sql:184-219`）：

| | hardening 版 | **trade_records_ref 版（09-10，更晚）** |
|---|---|---|
| `perform bot_buy_guard()` | ✅ | ❌ 缺 |
| `seller_id = auth.uid()` self 校验 | ✅ | ❌ 缺 |
| 写 `security_bot_buy_log` | ✅ | ❌ 缺 |
| `delete from equip_listings`（防重复收购） | ✅ 注释明写"防孤儿行被重复购买刷材料" | ❌ 只删 `equip_items`，**挂单行留在 `active`** |
| 前置 `drop function if exists` | ✅ | ❌ 无 |
| grant | — | ❌ `to anon, authenticated`（第 219/257 行） |

**后果**：如果线上最后执行的是 `trade_records_ref`（它 09-10 才加，很可能就是），那么 equip/pet 也是**无守卫**版本，且因为挂单行没删，同一条单可以**被反复收购**——`equip_items` 第二次删 0 行，但给卖家加材料的语句照样执行 = **纯凭空产材料，零成本**。

同一模式还波及 RLS：
- `migrate_material_trade.sql` 建了 `trade_records_open_all`（**所有人可读全部交易记录**），`migrate_security_hardening.sql` 删掉它换成 `trade_records_select_own`。重放 material_trade → 隐私泄露回退。
- `migrate_trade_records_ref.sql:180` 又 `grant execute ... to anon` 给 `buy_egg`，与 hardening 第 17-18 行"anon 全部收回"直接冲突。

**根因**：安全加固是"后加的收口脚本"，但仓库里**没有任何机制阻止更早的脚本被重放**。`PROJECT_CONSTITUTION.md` #2 自己承认了这个洞："迁移应用记录：谁按什么顺序应用了哪些 SQL、当前库停在哪个版本，无记录"。

### 先查线上到底是哪个版本
跑这条，一次看明白：

```sql
select p.proname,
       pg_get_functiondef(p.oid) ilike '%bot_buy_guard%'      as has_guard,
       pg_get_functiondef(p.oid) ilike '%security_bot_buy_log%' as has_log,
       p.proacl::text as acl
from pg_proc p
join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and p.proname like 'bot\_buy%'
order by p.proname;
```

`has_guard = false` 或 acl 里出现 `anon` → 就是洞。

### 修复（按懒到勤排序）
1. **立刻**：新建 `supabase/migrate_security_reapply.sql`，把三个 `bot_buy_*` 一起重定义成带守卫版 + `revoke ... from anon`。一个文件，别回头改旧的。
2. **立刻**：在 5 个会被覆盖的旧脚本**文件头加一行注释**：`-- ⚠️ 已被 migrate_security_reapply.sql 取代，重放会抹掉安全守卫，禁止执行`。
3. **等有第二个人维护时再做**：给迁移编序号（`001_`…）或建 `schema_migrations` 表。现在一个人做，注释足够。

## 🟠 P1-3　`applyCraft` 的重试逻辑会吞掉「装备词缀同步失败」　✅ 已修

`docs/js/equipment/equipment_craft.js:108-115`：

```js
let syncErr = (sp && sp.error) || (sp && sp.data === false ? new Error(...) : null) || (up && up.error);
if (syncErr && sp && sp.data === false && !sp.error) {
  await Materials.flushMaterials();
  const again = await Materials.cloudSpend(stoneName, stoneAmount);
  if (again && again.data !== false && !again.error) syncErr = null;   // ← 无条件清空
}
```

`sp` = 石头扣减，`up` = `Items.updateCloudItem`（装备词缀落库）。
当**两者同时失败**（石头余额不足 + 词缀更新失败），重试只重试 `sp`；`sp` 成功就把 `syncErr` 整个置 `null`，**`up.error` 被丢掉**。

结果：函数返回 `{ok:true}`，界面显示打造成功，石头扣了，本地词缀是新的，**云端词缀还是旧的**。玩家刷新 → 词缀回退。如果刚 roll 到 T1 词缀，就是白花石头 + 丢词缀。

**修复**：只清空"石头那一路"的错误——

```js
if (again && again.data !== false && !again.error) syncErr = (up && up.error) || null;
```

### 执行后复验（2026-09-11）

## 🔴 P0-1　`jsonb` 参数被 `JSON.stringify` → 幂等失效 → **所有玩家挂机产出被放大 1.4~2.1 倍**　✅ 已修并已上线

### 代码事实

`battle-settle/index.ts:202 / 208`：

```js
p_detail: JSON.stringify(plan.logDetail),
p_pending_script: JSON.stringify({ id: script.id, until: untilIso, script })
```

RPC 参数声明的是 `jsonb`（`migrate_battle_pending_script.sql:18,23`）。传 JSON 字符串过去，PostgREST 会把它当成**一个 JSON 字符串值**，而不是数组/对象 —— 于是落库是 `jsonb string` 而非 `jsonb array/object`。

线上实测（修复前）：

| 列 | 类型 | 行数 |
|---|---|---|
| `battle_logs.detail` | `string` | 7024 / 7024 |
| `idle_sessions.pending_script` | `string` | 64 / 64 |

### 为什么这是 P0

EF 读回 `session.pending_script` 得到的是**字符串**，于是这一行（`:136`）：

```js
if (pending && pending.script && pending.until && nowMs < ...) { /* 幂等：原样再发，不记账 */ }
```

`"..."` 字符串没有 `.script` 属性 → 恒为 `undefined` → **幂等分支永不命中** → 每次 `settle` 都往下走：重新模拟一个 **30 秒剧本窗**、推进游标、**再入账一次**。

### 线上铁证

如果幂等生效，同一个 30 秒窗口内的重复 `settle` **不会写 `battle_logs`**。实际：

| session | settle 次数(=日志行数) | 真实经过 | 授予的模拟时长 |
|---|---|---|---|
| `b9eb0405…` | 4 | 57 秒 | **120 秒 → 2.10×** |
| `e363ce76…` | 7 | 107 秒 | **≈2.0×** |
| `4de44b0a…` | 9 | 144 秒 | **≈1.9×** |
| `8f2f6867…` | 4 | 67 秒 | **≈1.8×** |
| `692470d9…` | 24 | 456 秒 | **≈1.6×** |

**每次 settle 都写了日志 = 每次都在记账。** 结论：不是"可以刷"，而是**全体玩家被动地多拿了 1.4~2.1 倍产出**。而 `add_material` 的限流（60 秒 1000 个）远高于这个量级，挡不住。

`battle_logs.detail` 存成字符串 → 任何按明细聚合的查询都直接报错（本次审计第一步就踩到了 `cannot extract elements from a scalar`）。

### 修复（两层，都已落地）

     —— 这一层让**洞立刻关上，不必等 EF 重新部署**；且旧数据在下次写入时自愈。
2. **修 `battle-settle/index.ts` 根因**：去掉两处 `JSON.stringify`，直接传数组/对象。

## 🔴 P0-3　RLS 只做「行归属」，不做「列/值」控制 —— 玩家能直连 REST 改自己的资产　🟡 已部分修复

### 事实

宪法 E2 写的是「RLS + RPC 只防外人直连，防不了**真人玩家改前端后**合法提交」。实际情况比这更直接：**根本不用改前端**，一条 `PATCH` 就行。

线上核对（`pg_policies` + `pg_constraint` + `pg_trigger`）：

| 表 | RLS 允许本人 | 约束 | 触发器 | 后果 |
|---|---|---|---|---|
| `materials` | INSERT / UPDATE / DELETE | **无任何 CHECK** | **无** | `PATCH … {"quantity": 999999}` → **凭空造材料** |
| `pets` | INSERT / UPDATE / DELETE | growth 1~100、level **1~99**（注意不是 60） | 无 | 改满成长 / 改 traits / 改觉醒 → 造神宠卖钱 |
| `equip_items` | INSERT / UPDATE / DELETE | 无 | 无 | 伪造全 T1 金装 → 卖钱 |
| `pet_egg` | INSERT / UPDATE | 无 | 无 | 造蛋 |
| `quest_progress` | upsert | 无 | 无 | 直接改进度领奖 |
| `wallets` | **仅 SELECT** | gems ≥ 0 | — | ✅ 魔石安全（写只走 RPC） |
| `profiles` | INSERT / UPDATE | 无 | 无 | 见下 |

**为什么这是 P0 而不是"自欺欺人"**：这游戏有**跨玩家真实交易**（材料计价的市场）。凭空造材料 → 挂单 → **换走别人真材料**。攻击者获益、受害者是其他玩家。跨了信任边界。

`profiles` 那条尤其难看：`profiles_update_own` 的 `with_check` 是 `auth.uid() = id`，只保证"只能改自己那行"，**不限制改哪些列**。而 `bot_buy_guard()` 正是用 `select banned from profiles where id = auth.uid()` 做封禁拦截 →
`PATCH /rest/v1/profiles?id=eq.<自己>  {"banned": false}` → **封禁形同虚设，被封的号自己解封即可。**

### 已修（能安全收口、不打断功能的两张表）

`supabase/migrate_asset_write_hardening.sql`（已上线）：

1. **`materials`——客户端只读，写入一律走 RPC**
   依据：全仓核对，客户端对 `materials` 只有 2 处用法，**都是 `select`**（`core/materials.js:170`、`ui/ui-shop.js:190`）；所有写入走 `add_material` / `spend_material`（两者 `security definer`、owner=`postgres`，不受 RLS 与列级权限影响）。
   做法：删掉三张写策略 + `revoke insert, update, delete on public.materials from authenticated, anon`。
   （只删策略也能挡住 —— RLS 无策略 = 默认拒绝 —— 但表级授权留着会让以后审计误判，所以两层一起收。）

2. **`profiles`——列级权限收紧**
   `revoke update/insert on profiles from authenticated` + `grant update (id, nickname, avatar_url)`。
   依据：客户端对 `profiles` 只写 `{id, nickname}`。`admin_*` 全是 `security definer`，不受影响。

### ❌ 没修的（收掉会直接炸功能）

`pets` / `equip_items` / `pet_egg` / `quest_progress` / `*_listings` —— **客户端的整个架构就是"直接写自己那行"**（`updatePet`→`pets.update`、`Items.updateCloudItem`→`equip_items.update`、`consumeEgg`→`pet_egg.update`…）。收掉策略等于当场打断宠物/装备/孵蛋全部功能。

## 🟠 P1-3　`nirvana` 两种失败模式**都会出事**（一只不可逆的操作排在了可逆操作前面）　✅ 已修

`pet_merge.js:251-268`：

```js
const delSub = await Supabase.deletePet(sub.cloudId);        // ① 删副宠（不可逆）
if (delSub.error) { console.warn(…); /* 副宠留下 */ }
else { removePet(sub.id); }
…
const { error: updErr } = await Supabase.updatePet(main.cloudId, patch);   // ② 更新主宠
if (updErr) console.warn('云端更新宠物失败：', updErr.message);             // ← 只 warn，然后返回 {ok:true}
```

| 失败点 | 结果 |
|---|---|
| ② 失败 | 副宠**已经永久删除**，主宠成长**没涨** → 玩家**白亏一只副宠**；函数仍返回 `{ok:true}`，界面显示涅槃成功 |
| ① 失败 | 副宠留在列表里，但主宠**照样涨了成长** → 玩家可以拿**同一只副宠再涅槃一次** → **白刷成长** |

也就是说：两种失败都不是"安全失败"。而 `deletePet` 是**不可逆**的 —— 先删它就等于把整单的原子性交给了后续操作。

### 修复（2026-09-11 已落地）

**核心原则：不可逆的操作必须排在最后。** `deletePet` 删了就回不来，所以它只能当最后一步；它前面的每一步失败都必须整单回滚。

```
① 快照主宠旧值（含 traits 深拷贝——implantNirvanaTraits 在原数组上 push）
② 更新主宠（可逆）
     └ 失败 → 还原主宠本地值 + 退回已扣道具 → 报错。副宠没动，零损失
③ 更新成功 → 删副宠（不可逆）
     └ 失败 → 把主宠写回旧值（云端 + 本地）+ 退回道具 → 报错。副宠仍在，可重试
```

两个容易漏的点，都补了：
- **道具必须一起退**。前面已经扣了涅槃丹 / 凝魂晶石 / 锁魂玉；只还原宠物不退道具，等于把"白亏一只副宠"换成"白亏材料"。
- **`traits` 要深拷贝**。`implantNirvanaTraits` 是在 `main.traits` 原数组上 `push` 的，浅拷贝存快照会被一起改掉，回滚就成了空操作。

**测试**（`vtest_god_pet.js` 第 7 节，8 条新断言）：注入 `updatePet` 失败 / `deletePet` 失败，分别断言"如实报错 + 道具退回 + 成长未变/已回滚 + 副宠仍在"。

**仍未解决的（更彻底的做法）**：这条链**没有事务**，和第 1 批的 P1-1（发奖与记账不在同一事务）是同一个病。上面的补丁把两种**明确的**失败模式都堵住了，但"第 ② 步成功、进程在 ③ 之前崩掉"这种仍会留下不一致。终局要 `nirvana_pet(main_id, sub_id, …)` 服务端事务 RPC —— 归入「服务端权威」那批。

## 🟡 P2-1　客户端更新无法区分「改成功」和「一行没改到」　✅ 已按 **opt-in** 方案修（不全局面铺）

### 事实

`supabase-js` 的 `.update()` 不带 `.select()` 时，PostgREST 不返回受影响行 → **"行不存在"和"更新成功"都表现为 `{data:null, error:null}`**。

全客户端普查（`.update(` 后有没有接 `.select(`）：

| 位置 | 写法 | 后果 |
|---|---|---|
| `core/supabase.js:197` | `pets.update(p).eq('id', cloudId)` | ❌ 无 |
| `core/supabase.js:204` | 同上（缺列重试分支） | ❌ 无 |
| `core/items.js:42` | `equip_items.update(patch).eq('id', eq.cloudId)` | ❌ 无 |
| `core/supabase.js:174` | `pets.update({equipment}).eq('id', ...)` | ❌ 无（有 try/catch 兜底，风险低） |
| `core/supabase.js:413` | `pet_egg.update({...}).eq('id', data.id).select().single()` | ✅ **有**（`.single()` 在 0 行时报 `PGRST116`） |

**调用方全部只解构 `{ error }`**（`main.js:78`、`pet_merge.js:293/307/572`、`pet_evolve.js:199`、`equipment/equipment.js:278`、`ui/ui-dev.js:532`、`ui/ui-pet-awaken.js:143`、`equipment_craft.js:104/314/384`、`salvage.js:35`… 无一使用 `.data`）—— 所以**加了检测不会破坏任何调用方**，这一点是安全的。

### 为什么它要紧

- `updateCloudItem` 0 行 → 打造报成功、石头扣了，**云端词缀没落库**，刷新即回退。
- `updatePet` 0 行 → **这正是 P1-3 的一条残余通道**：主宠行已被另一个标签页删掉时，`updErr` 是 `null`，我刚加的检查挡不住 → 于是流程继续往下走、**把副宠删了**。
  （另一条常见的"行消失"通道 —— 宠物在别的标签页被卖掉 —— 被 `Market.isListed` 挡着，所以实际触发需要**多标签**这种不常见操作。概率低，但性质是丢资产。）

### 全量调查（改任何代码之前做的）

**判据**：「0 行会导致丢资产吗？」

**`updatePet` 的 14 个调用点**：只有 3 个是"先扣东西、后写云端"的不可逆链条 —— 涅槃主宠 / 进化 / 培育。
其余 11 个（挂机经验写回、装备槽防抖同步、切出战宠、补 traits、dev 面板…）0 行只是"没同步上"，下次操作会重来，**不该打断**。

**`updateCloudItem` 的 6 个调用点**：只有 2 个该拦 —— 打造（石头扣了词缀没落库）/ 魂铸（晶石扣了 + 宠物删了、词缀没落库）。
鉴定、解锁锁定这类 0 行只影响体验，不值得为它加一次往返。

**结论：不该全局加。** 全局面铺会连带改 5 个"用假 `cloudId` 造数据"的测试（`vtest_craft_lock` / `vtest_trait_soulcast` / `vtest_affix` / `vtest_idle_bridge` / `vtest_equip_persist`），而那些失败**不是产品缺陷、是测试卫生** —— 让测试先真建档属于另一件事。

### 实际做法：opt-in

```js
updatePet(cloudId, patch, { verify: true })          // 只有不可逆链条传
updateCloudItem(eq, patch, { verify: true })
```

传了才加 `.select('id')`，0 行 → 返回明确错误（"这只宠物已不在你的存档里（可能在别的标签页被出售或删除），本次改动未生效"）。**其余 15 个调用点一个字不改、行为不变。**

开了 verify 的 6 处：`pet_merge.js` 涅槃主宠 / 涅槃回滚 / 培育、`pet_evolve.js` 进化、`equipment_craft.js` 打造 / 魂铸。

### 测试桩配套（纯增量）

`vstub.js` 原来 `update().eq()` **只返回 `{data:null,error:null}` 且不支持 `.select()`** → 真代码一调就 `res.select is not a function`。给它加了 `select`（不动原 `then`，所以其他测试零影响）：

```js
select:()=>({then:(res)=>{ …; res({data: r ? [r] : [], error:null}) }})
```

### 验证

- **全量回归 66/72，与基线完全一致** → **实际波及 0 个测试**（比"只改 6 处"的预期还干净）
- `vtest_god_pet.js` 新增 3 条断言：verify 更新不存在的行→报错 / 不开 verify→保持原行为 / verify 更新存在的行→正常成功

> ⭐ **这次的做法值得复用**：先出「全量消费方清单 + 该不该拦」的判定，再选**最小作用域**的改法 —— 而不是先把检测全局加上再看谁炸。用户 2026-09-11 明确要求「不要过度堵住，要结合所有代码之后才知道结果」。

## 🟠 P2-3　`compensateFights` 的兜底分支是一条「静默双倍发奖」通道　✅ 已修

### 事实

`idle-bridge.js` 有 **2 处**这样的代码（`compensateFights` 与演出层的 `finishShowFight`）：

```js
const serverReward = row && hasOwnProperty(row, 'reward') ? row.reward : null;
if (serverReward) {
  Materials.gainLocal(...)              // ✅ 纯本地，云端由服务端 add_material 已发
} else if (area && foe && Drop.rollReward) {
  Drop.rollReward(foe, area, { boss, enemyLevel })   // ❌ 没传 dry → 真发奖
}
```

而 `drop.js#rollReward` 在**不传 `dry`** 时会真的落库：

| 行 | 动作 |
|---|---|
| `drop.js:134` | `Materials.gain(am.name, 5)` → **上报云端 `add_material`** |
| `drop.js:140` | `Items.saveItem(eq)` → **写库一件装备** |
| `drop.js:201` | `Supabase.addEgg(baseName)` → **写库一颗蛋** |

注释自己写着「新战报的 reward 已由服务器决定；页面只负责入包和展示」+「兼容旧版战报（没有 reward 字段）时才走旧掉落逻辑」——**它本意就只是"演出来"，但实现给了它真发奖的能力。**

### 为什么现在没炸，但它很危险

服务端 `withReward` **总会**塞 `reward` 字段 → 这个 `else` 分支**当前是死代码**。

但它是"危险兜底"：一旦服务端因为任何原因不再下发 `reward`（字段改名、回滚到旧版本、某个路径漏塞），客户端会**静默地自己发一份并上报云端** → **每场战斗双倍产出**，而且**没有任何日志、没有测试能发现**。这种"静默翻倍"是最难查的一类。

### 修复

两处都加 `dry: true`：

```js
Drop.rollReward(foe, area, { boss, enemyLevel, dry: true })
```

`dry` **仍然返回抽样结果**（`showLoot` 照常展示掉落），只是不落库、不上报 —— 正好就是"兜底只该负责演"想要的语义。

> ⭐ **原则**：**发奖权已经归服务端之后，客户端那份兜底就不该保留发奖能力。** 留着不是"保险"，是"静默双倍"的入口。

`?v= idle-bridge dry1`；全量 67~69/73（见下方 flaky 说明）。

## 🔴 P0-4　腐印（腐蚀度）从第二局起**永久免费** —— 结算面板「再打一次」就能触发　✅ 已修

### 代码事实

`tower/tower-engine.js#start`（修复前）：

```js
const access = await window.TowerAccess.consumeEntry();   // ① 扣免费次数 / 重置卡
if (!access.ok) return { ok: false, error: access.error };

// 腐印是一次性消耗品：进入时扣掉（校验已过，这里按条扣）
if (ids.length && window.Materials && window.Materials.spend) {
  for (const id of ids) {
    const spent = await window.Materials.spend(name, 1);
    if (spent && spent.ok === false) {
      log(`⚠️ ${name} 扣除失败：${spent.error || '数量不足'}`);   // ← 只打一行日志
    }
  }
}
state.running = true;   // ② 照样进塔，combo 照常生效
```

**扣腐印失败 = 只 `log()`，不中断。** 而 `state.combo = TowerAffix.combine(ids)` 是基于**传入的 ids** 算的，跟有没有真扣下来毫无关系 → 掉率增益（装备 +X% / 材料 +Y%）照拿。

`TowerAffix.validate(ids)` 只校验「条数上限 / 不可读组合同局最多 1 条 / 不许重复贴」，**完全不校验库存**。UI 侧唯一的库存守门是 `ui-tower-entry.js:53` 的 `${own <= 0 ? 'disabled' : ''}` —— 一个 HTML 属性。

### 触发路径：不用改前端，点按钮就行

`ui-tower-settle.js:180-185` 的「再打一次」：

```js
// 再打一次沿用本局腐印（腐印已消耗，缺货时引擎会拦下并回详情页）
if (UI.startTowerBattle) await UI.startTowerBattle(result.affixIds || [], { from: 'settle' });
```

**注释写的和代码做的是两件事。** 腐印在上一局进场时已扣掉，库存必然是 0 → `spend` 必失败 → 只 `log()` → **照样进塔、腐蚀度照旧、掉率增益照拿**。

也就是说：**从第二局开始，玩家手里的腐印变成永久 buff**，一局都不用再消耗。

对照 `trial` 的同一个「再打一次」（`ui-trial-settle.js:75`）—— 那条是安全的，因为门票走 `consumeEntry`，失败会 `return { ok:false }` 并被 `startTrialBattle` 接住弹 toast。**同一个按钮，副本那条安全、塔这条能白嫖。**

### 为什么是 P0 不是 P1

- 宪法 B10 红线：**「消耗端必须存在（sink）」**。腐印是专门为塔设计的材料 sink（结算面板自己写着「腐印（N 种）· 进塔的门票，也可上架」）。sink 归零 = 塔的产出没有对应消耗。
- 掉率增益能**换算成材料/装备**，而材料能挂单卖给其他玩家 → 跨信任边界（与第 2 批 P0-3 同一判据）。
- 触发成本 = **点一下按钮**。不是"改前端才能利用"。
- ⚠️ 有人会说"腐印同时也强化怪，白嫖要付难度代价" —— **这不能成为 sink 失效的理由**：sink 的意义就是"要拿增益就得消耗"，难度是另一回事。

### 修复（已落地，三处）

1. **腐印库存预校验**（`tower-engine.js#start`，在 `TowerAffix.validate` 之后、`consumeEntry` 之前）：
   按**名字聚合**（同名贴多条只算一次总量）算出 `affixNeed`，任一种不够就 `return { ok:false, error:'缺少「X」×N（腐印进入时消耗）' }`。
   —— 放在扣任何东西**之前**，所以不需要"扣了再退"。
2. **扣减失败整单放弃 + 退回已扣**：预校验过了还失败 = 别的标签页刚花掉。此时 `refundAffix()` 把已扣的退回去再报错。
3. **扣腐印改排在 `consumeEntry` 之前**（腐印比"免费次数/重置卡"容易退）→ 资格扣失败时只要 `refundAffix()` 即可。

> ⭐ **顺序原则：容易退的先扣，难退的后扣。扣不动就整单放弃，不要"只 log 继续"。**

## 🟠 P1-8　"发奖后必须 flush" 这条自己定的规矩，只有一半调用点遵守　✅ 部分修（塔/副本）

### 事实

`materials.js:57-61` 自己写着：

### 为什么它要紧

`gain` = `gainLocal`（本地立刻显示）+ `enqueue`（**4 秒后**才上报）。这 4 秒里：

- **塔一局几十分钟**，结算拿到一堆材料 → 只入队 → 玩家看完结算面板关页面 → **一局产出凭空消失**
- **进化失败退素材** → 刷新 → 素材没了 → **玩家白亏一份进化素材**（亏两次：先扣了、退款又没落盘）

### 兜底（所以定 P1 不是 P0）

`main.js:744-750` 的 `visibilitychange`（hidden）会 flush 一次。**切后台/关标签页大多能救回来**，但它：

1. 不 await（关页面时的异步请求常被浏览器掐掉 —— `main.js:742` 自己的注释承认了这点）
2. 浏览器崩溃 / 强制退出时不触发
3. `spend` 会顺带 flush（line 95）→ 所以"退款后玩家立刻重试"这条路径是安全的

### 修了什么（最小作用域）

**只在塔和副本的 `finish` 里各加一次 `await Materials.flushMaterials()`**（一局一次）。

- 不动层掉落那几十次 `gain`（每次 flush = 一次 340ms 往返，会卡演出）
- 不动宠物资产链的退款路径 —— 那 6 处失败后玩家通常会立刻重试，`spend` 会顺带 flush；为它加 6 次往返不值得。**记为建议**：要是以后有玩家报"进化失败后刷新素材没了"，补 flush 就是。

> ⭐ **又是一次「同一类操作只有一半做对」**：发奖 flush 了、退款没 flush。与第 9 批的"tower 有 try/catch、trial 没有"是同一种病。

# 第 13 批：`idle-bridge.js` 三处（不再依赖子代理，逐行读码后改）

第 11 批那 5 条"待复核"里，我逐行读了 3 条并修掉。**子代理的行号是对的，但对"后果"的描述需要自己验一遍才敢下手。**

## 🟠 1　`callFn` 裸 `fetch` 无超时 → 一次挂起就把整个模块锁死

```js
const res = await fetch(FN_URL, { method: 'POST', ... });   // 无 signal
```

`fetch` 在连接挂起（不是断网，是服务器不响应）时**可以永远 pending**。而 `settleNow()` 用 `settling` 布尔锁串行化：

- 一次挂起 → `settling` 永远为 true
- L889 `if (!settling && now >= nextScriptTryAt) settleNow()` 永远被挡 → **拿不到新剧本**
- 兜底 `tick()` 里的 `settleNow()` 被同一把锁挡住 → **兜底链一起断**
- 结果是**画面不动、控制台干净、零日志** —— 最难查的一类故障

**修法**：`AbortController` + 15 秒超时，把"未知的挂起"变成"确定的失败"（`'TIMEOUT'`），让上层的重试逻辑能真正跑起来。

> ⭐ **模式：任何"布尔锁 + 网络请求"的组合，请求都必须自带超时。** 否则锁的释放依赖于对方一定会回话。

## 🟠 2　`start()` 的闸门挡不住并发 → 两条 rAF 同时推进

```js
if (active) return { ok: true };        // 唯一闸门，在 await 之前
const r = await callFn({ action: 'start', ... });   // ← 网络往返
active = true; startShow();             // ← 回来才置真
```

连点两次：两次都通过闸门（此时 `active` 还是 false）→ 两次 `callFn('start')`（服务端"停旧建新"执行两遍）+ 两次 `startShow()`。而 `startShow` 里 `gaugeRaf = requestAnimationFrame(...)` **会覆盖句柄**，第一个循环取消不掉 → 两条 rAF 同时推进行动条、重复结算。

**修法**：加 `starting` 闸门（覆盖整个 await 区间）。

**顺带修了一个子代理没提的**：`callFn` 期间若被副本/塔抢占（`SESSION.onChange → shutdown`），回来后仍会 `active = true; startShow()` —— **在没持有战斗页的情况下起演，与抢占者抢同一套 DOM**。所以 await 之后加了一次占用权复查。

## 🟡 3　`stopShow()` 不复位 `waitingHeal`，也不收立绘

`startShow()` 里清了 `waitingHeal = false`，`stopShow()` 没清 → 停机后 `!showEnemy && !waitingHeal` 这条血量对齐分支**永远不成立**，收尾 settle 时宠物血量对不上服务器真账。

同时 `#enemy-fighter` 没隐藏（`finishShowFight`、`enterHealWait` 都显式隐藏了，就 `stopShow` 漏了）→ 打怪中途停机/被抢占，**怪的立绘留在画面上**。

两个都在 `stopShow` 里补齐，与 `startShow` 成对。

| 权限 | 收掉表级 INSERT/UPDATE/DELETE，改成**列级**：客户端只能写 `user_id/progress/updated_at`，**`claimed` 只有 SELECT** |
| RPC | `complete_quest(qid, period_key)`（security definer）：查 `claimed` → 已有该键返回 `ALREADY_CLAIMED`，否则写入。anon 不可调 |
| 管理 | `admin_unclaim_quest()`：只有管理员邮箱可调，**authenticated 不在 ACL 里**（玩家不能自己解封 —— 同 `profiles.banned` 教训） |
| 客户端 | `quest.js#completeQuest` 在**扣材料之后、发奖之前**调一次；失败退回材料 + 撤销本地标记 |

**键的设计**：一次性任务 = 任务 id（永久唯一，玩家伪造周期键也没用）；日常 = `id@当天`；周常 = `id@本周一`。分流口径与 `isFinished`/`markFinished` 完全一致。

**顺序为什么是"扣材料 → 占位 → 发奖"**：材料**能退回**，占位**退不回**（退回去等于又能重领一次）。所以"容易退的先扣、难退的后扣"—— 这是第 9 批总结的原则，这次又用上了。

## ⚠️ 三个自己踩的坑（都是"过度堵住"）

**1. 给 `repeatable` 任务做了永久占位** → 把设计上无限重复的任务改成了一次性。

`d1`（每日巡守）是 `repeat: true`，`isFinished` 走 `dailyDone`。我一开始没排除 `repeatable`，结果测试里"交完被追踪的日常任务"直接红。**修法**：`!q.repeatable` 才占位 —— 这一类本来就是无限次，不该堵。

**2. 把"没拿到确定答复"也当成拒绝** → 弱网玩家交不了任务。

supabase-js 网络失败是**返回 error 对象，不是抛异常**。我最初 `claim.error || ALREADY_CLAIMED` 一律拒绝，结果 `vtest_deep2` / `vtest_guide_grant` 两个测试变红（它们用真实 RPC、无网络）。

**修法**：**只有服务端明确说 `ALREADY_CLAIMED` 才拦**；网络错误 / 未登录这类"没拿到确定答复"的情况降级放行 + 留痕。理由：断网时 `Materials.spend` 同样会失败、收集类任务本来也过不去，这个降级换不来多少收益，却能救回弱网体验。

**3. 测试桩没模拟"换号"语义**。

`vtest_quest` 的 `hardReset()` 模拟换号（清空 `questTable`），但服务端 `__questClaims` 没跟着清 → 变成"换号也领不了"。**修法**：`hardReset` 清、`reload`（刷新页面）不清 —— 后者正是"云端留着"该有的行为。

## 已知边界（如实记录）

1. **日常/周常的周期键由客户端传** —— 玩家改前端伪造新周期键可在同一天多领一次日常。收益低（日常 100 经验 + 少量材料）且要改代码。**彻底堵需要把任务定义（id → reset）同步到服务端**，下一步。
2. **一次性任务（主线 / 成就 / 新手 / 宠物）被彻底堵死** —— 奖励最厚的正是这一类。
3. **不追溯历史**：上线前已领过的一次性任务，每人还能再领一次（老行 `claimed` 为空）。
4. **任务进度（打怪计数）仍是客户端权威**，改前端可伪造达标。本批不解决 —— 那要把整个任务系统搬服务端。

**最大的两个系统性病因**（不是单个 bug，是"病"）：

1. **「注释说了 A，代码做的是 B」** —— 11 批里有 6 个问题是这个模式（腐印"引擎会拦下"、makeGear"不能丢"、tower"发奖异常要弹面板"、materials"发奖后要 flush"、shop"连点不会重复扣"…）。**注释是最容易被当成已实现的需求**，也是审计时性价比最高的意图源。
2. **「同一份逻辑复制两遍/三遍，只有一份是对的」** —— tower/trial、发奖/退款、鉴定两处。修一处要顺手 diff 另一处。

**没修、也不该在审计里修的**：所有"客户端权威"类（改 localStorage 无限进塔、改前端必胜、直接 REST 改资产）。正解是宪法 #1 的服务端权威化，是工程量不是补丁。
