### 1.3 五个问题（大白话版）

1. **有两张表"库里有、但代码仓库里没建表 SQL"**：`quest_progress`、`spend_material` 函数。
   意思是：万一哪天要重建库，这俩就凭空消失了，任务系统会 400 报错。**必须补文件**（零风险，纯补文档）。
2. **三张挂单表结构几乎一样**（宠物 / 装备 / 蛋各一张）。以后要加"材料挂单"还得再建一张。
   —— 现在**不合并**，合并要改前端 + 迁数据，自测阶段不值得。记在账上，等哪天要加第四种再说。
3. **挂单表里有废弃的 `price` 列**（改成材料计价后就没用了，留着为兼容旧数据）。不删，删了旧行会报错。
4. **`trade_records` 没记交易对手**：现在 `player_id` 是 text，真实玩家存 uuid、NPC 存"流浪商人"三个字。
   玩家查"我卖给了谁"查不出来。上线前建议补 `counterparty`、`listing_id` 两列（增量加列，安全）。
5. **经验（exp）不存云端**：等级、成长值、进化次数、涅槃次数、装备槽都上云了，但**当前等级的经验条没上云**。
   表现为：刷新页面等级还在，经验条清零重新攒。自测阶段无所谓，上线前补 `exp` 列即可。

### 1.4 一个必须在上线前堵的洞

现在**任何人拿到项目里那个公开 key，就能反复调 `add_material` 给自己刷材料**（掉率是浏览器算的，云端只负责加）。
自测阶段无所谓（就你自己在玩），但只要有真实玩家，这就是白嫖漏洞。
修法见 §5 上线前清单。

## 2. 目标表设计

### 2.1 分批原则

| 批次 | 内容 | 什么时候做 | 为什么 |
|---|---|---|---|
| **第一批** | `profiles` + `wallets` + `wallet_ledger` | **现在就建** | 自测阶段建表零成本，且后面所有功能（昵称、权益、付费）都依赖玩家档案。先占好坑 |
| **第二批** | `products` + `orders` + `payment_events` + `entitlements` + `redeem_codes` | 要开始收钱前 | 卡密闭环的全部家当 |
| **第三期** | `mail` + `security_events` | 有真实玩家后 | 补发、风控 |

**原则：第一批表全是"新增"，不碰现有 10 张表的一行一列。** 所以老功能零风险（上次给 pets 加 equipment 列把宠物读爆的教训，不会再犯）。

---

### 2.2 第一批：玩家与钱包

#### `profiles` —— 玩家档案

现在完全没有这张表，昵称、封禁、最后在线时间都无处可放。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid PK → auth.users(id) | 注册即自动建一行（触发器） |
| nickname | text unique | 显示名，默认用邮箱前缀 |
| avatar_url | text | 头像（将来卖头像框用） |
| invite_code | text | 注册时填的邀请码（现在 config 里有 SOUL2026） |
| created_at | timestamptz | 注册时间 |
| last_seen_at | timestamptz | 最后在线（将来做"日活"、回归奖励用） |
| banned | boolean default false | 封号 |
| ban_reason | text | 封号原因 |

RLS：自己可读可改自己的行；所有人可读别人的 nickname/avatar（市场要看卖家名字）。

#### `wallets` —— 充值币（魂晶）余额

一行一个玩家。**这张表前端永远只能读，不能写**。

| 字段 | 类型 | 说明 |
|---|---|---|
| user_id | uuid PK → auth.users(id) | 注册时自动建一行，gems = 0 |
| gems | int default 0 check (gems >= 0) | 魂晶余额。**余额不能为负**，靠数据库约束兜底 |
| total_recharged | int default 0 | 累计充值获得（算 VIP、对账用，只增不减） |
| updated_at | timestamptz | |

> 为什么余额要单独一张表、不直接塞进 profiles？
> 因为余额是**最敏感的数字**，要单独加锁（扣款时锁这一行），不能让它跟昵称之类的一起被随便改。

#### `wallet_ledger` —— 魂晶流水（append-only）

每一笔魂晶变动都记一条，**不能改、不能删**。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigserial PK | |
| user_id | uuid | |
| delta | int | 变动量，正数是加、负数是扣 |
| balance_after | int | 变动后余额 |
| reason | text | 充值 / 消费 / 退款 / 补偿 / 管理员发放 |
| ref_type + ref_id | text | 关联到哪笔订单、哪张卡密 |
| created_at | timestamptz | |

> 为什么必须有这张表？
> 玩家来问"我明明充了 60 块，钻呢？"——你查这一张表，一笔一笔都摆在那。
> 没有它，你永远说不清，只能靠猜。**这是所有游戏公司的标配，没有它必被薅羊毛。**

RLS：只能读自己的，任何人都不能 insert/update/delete（写入只有服务端函数能做）。

### 2.4 第三期（有真实玩家后再建）

- **`mail`** —— 邮件：发货失败补发、全服补偿、活动奖励。带附件 JSON（补偿几个材料、几颗魂晶）。
  为什么需要：只要出现过一次"扣了钱没到账"，你就得有个地方能精准补给这一个玩家，而不是全服广播。
- **`security_events`** —— 风控流水：谁 1 分钟内加了 999 个材料、谁一天换了 5 台设备登录。

## 3. 服务端函数清单

### 现有（12 个，不动）

`add_material` `spend_material` `buy_pet` `buy_equip` `buy_egg` `list_egg`
`cancel_pet_listing` `cancel_equip_listing` `cancel_egg_listing` `bot_buy_pet` `bot_buy_equip`

### 新增（付费用，4 个）

#### ① `redeem_code(p_code text) → text` —— 卡密兑换

在一个事务里做完（要么全成，要么全不成）：

1. 没登录 → `nologin`
2. 锁住这张卡密那一行（`for update`）→ 并发兑换也只会成功一次
3. 不存在 → `notfound`；用完了 → `used`；过期了 → `expired`
4. 查 `products` 拿发货内容
5. 给魂晶：`update wallets set gems = gems + N, total_recharged = total_recharged + N`
6. 写一条 `wallet_ledger`（reason = `redeem`，ref = 这张码）
7. 非消耗类权益写 `entitlements`
8. 写一条 `orders`（status = `delivered`，provider = `redeem`）
9. 卡密 `used_count + 1`
10. 返回 `ok`

#### ② `spend_gems(p_sku text, p_client_ref text) → text` —— 用魂晶买东西

1. 没登录 → `nologin`
2. 查 `products`；不存在或已下架 → `notfound`
3. 限购校验（查 `entitlements` 里这人买过几次）
4. **锁住这个玩家的 wallets 那一行**（`for update`）——防止连点两次扣出负数
5. 余额不够 → `insufficient`
6. 扣款 + 写流水（delta 为负）
7. 按 payload 发货，写 `entitlements`
8. 返回 `ok`

> 关键点：第 4 步的行锁 + 第 5 步的余额校验必须挨着，中间不能有任何 await。
> 这就是"为什么余额只能服务端改"的技术原因——浏览器里的判断，玩家改一下 JS 就绕过去了。

#### ③ `grant_gems(p_user_id uuid, p_amount int, p_reason text)` —— 管理员发放

只允许特定管理员账号调用（函数里硬编码校验 `auth.jwt() ->> 'email'`）。
**自测阶段就靠这个给自己发魂晶测功能**，不用真的付款。

#### ④ `get_my_wallet()` —— 查余额

返回自己的魂晶余额 + 已购权益列表。前端只能调这个读。

## 4. 付费系统设计

### 4.1 卖什么（只卖外观和便利）

原则：**卖"省事"和"好看"，绝不卖"变强"**。这游戏的核心快感是"掉宝那一刻"和"市场捡漏"，卖数值等于自己拆自己的台。

**A. 外观（零风险，毛利最高）**

| 商品 | 说明 |
|---|---|
| 宠物染色 | 已有 40+ 形态立绘，做几套配色换皮 |
| 称号 / 头像框 | 聊天和市场上显示 |
| 聊天气泡样式 | |
| 掉落特效升级 | 金装扫光 / 稀有材料提示的视觉升级版 |
| 宠物展示背景 | 宠物页背景框 |

**B. 便利（最有付费意愿，且不破坏平衡）**

| 商品 | 说明 |
|---|---|
| **市场摊位 +5** | 现在 `config.trade.maxListings = 5`，这是最自然的付费点 |
| 自动分解白装 | 打完自动把白装换成打造石，不用手动点 |
| 掉落筛选/黑名单 | 自动忽略不想要的部位 |
| 宠物栏位扩充 | 需要先把"宠物数量上限"这个限制做出来 |
| 装备方案预设 | 存几套配装一键切换 |

**C. 时间类（放到最后，工程量最大）**

战斗加速、离线挂机收益 —— **这两个必须先把战斗和掉落逻辑搬到服务端**才能做。
现在掉率是浏览器算的，加速功能等于给玩家开了个"我说了算"的开关。

**D. 红线：绝对不卖**

- 宠物成长值、等级、经验
- 装备词缀、稀有度、T 阶
- 稀有宠物 / 宠物蛋
- **打造通货（重铸石 / 神圣石 / 增缀石 / 剥离石）** ← 你已拍板不卖
- 市场交易特权（免手续费、优先展示）

**不卖通货的理由再强调一遍**：玩家市场是用材料计价的。官方一旦卖材料，
玩家辛苦打的货就卖不上价，挂单没人买，"捡漏"和"卖个好价钱"这两个爽点同时死亡。
这个游戏的灵魂是玩家之间的经济，官方最好不要下场印钞。

### 4.2 卡密流程（现在走这条）

```
你后台生成一批码（插 redeem_codes 表）
        ↓
玩家微信/支付宝转钱给你（你个人收款码）
        ↓
你把码发给他（微信/QQ/邮件）
        ↓
游戏内输入码 → 调 redeem_code() → 魂晶到账
        ↓
玩家用魂晶在商店里买外观和便利
```

你卖的其实是"魂晶充值卡"，比如：

| 卡 | 价格 | 给多少魂晶 |
|---|---|---|
| 小袋魂晶 | 6 元 | 60（+6 赠） |
| 中袋魂晶 | 30 元 | 320（+40 赠） |
| 大袋魂晶 | 98 元 | 1080（+180 赠） |

**为什么先走卡密**：不需要企业营业执照、不需要备案域名、不需要接支付接口、不需要处理退款和风控。
个人开发者今天就能收钱，等跑通了、有了量，再上支付商。

### 4.3 将来接支付商怎么接（现在只留接口，不实现）

等你决定接了，只需要加一个中间层（Supabase Edge Function 或 Cloudflare Worker）：

1. 前端点"购买" → 调你的接口 → **服务端**查 products 拿价格 → 去支付商下单 → 返回支付链接
2. 玩家付款 → 支付商回调你的接口
3. 你的接口：**验签**（确认这真是支付商发的，不是玩家伪造的）→ 查 `payment_events` 看这个 event_id 处理过没（**幂等**，防重复发货）→ 发货（加魂晶 + 写流水 + 订单置为已发货）→ 返回 200 给支付商

因为订单表和发货逻辑现在就按这个结构设计好了，将来接的时候**前端不用改**，只是多写一个回调接口。
`orders.provider` 字段已经预留了 `creem` / `paddle` / `wechat` 这些值。

> 渠道建议：个人开发者优先 Creem / Paddle / Lemon Squeezy（对个人友好，他们替你处理收款和开票）。
> 微信/支付宝需要企业营业执照 + 备案域名 + 游戏类目，个人基本办不了，等有主体再说。

### 4.4 四条安全底线

1. **魂晶余额只有服务端能改**
   `wallets` 和 `wallet_ledger` 关掉所有写权限，前端只配调函数说"我要买这个"。
2. **价格在服务端定**
   前端只传 sku，金额由服务端查 `products` 写入订单。前端改价格改不动。
3. **回调验签 + 幂等**
   支付商通知必须验签；同一个 event_id 只处理一次（靠 `payment_events` 的唯一约束）。
4. **发货和记账一起提交**
   加魂晶 + 写流水 + 订单置为已发货，一个事务完成。要么全成要么全不成，不会出现"扣了钱没到账"。

## 5. 三张清单
