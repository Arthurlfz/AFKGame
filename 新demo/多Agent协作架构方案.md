# Forge of Souls · 多 Agent 协作架构方案

> 目标：用多个专职 Agent 协作开发 / 迭代这款「挂机养宠 + 真实交易」暗黑风游戏，按角色分配底层模型。
> 已确认：**策划 / 架构 → DeepSeek**；**写代码（后端 + 前端）→ GPT**。
> 当前项目位置：`d:/Ai/游戏原型/新demo/`（设计文档 + `Mvp/` 代码骨架）。

---

## 1. 模型分配

| Agent 角色 | 职责 | 绑定模型 | 理由 |
|---|---|---|---|
| 策划 / 数值 Agent | 读设计文档，产出需求、数值、MVP 边界，维护数据地图 | **DeepSeek** | 中文长文理解、数值推理强 |
| 系统架构 Agent | 模块划分、DB schema、接口契约、config 结构 | **DeepSeek** | 需要全局推理与一致性强 |
| 后端 Agent | Supabase SQL / RPC / 触发器（migrate_*.sql） | **GPT-5.6（中转站）** | 代码生成稳、SQL 准确 |
| 前端 Agent | Web UI：挂机战斗、背包、市场、宠物合成/进化/涅槃 | **GPT-5.6（中转站）** | 代码生成稳、JS 熟练 |
| 测试 / 自测 Agent | 删档自测、回归、链路校验 | **GPT-5.6（中转站）**（或 DeepSeek） | 读代码 + 写用例 |

> 说明：架构 Agent 用 DeepSeek 而非 GPT，是为了让「设计意图→结构」这一环不被代码模型带偏；如果你更想全程 GPT 只让策划用 DeepSeek，也可调整。

## 2. 共享知识库（所有 Agent 必读，避免各写各的）

- `游戏设计理念，所有Agent必须阅读.md`（核心循环、宠物/装备/市场机制、MVP 边界）
- `游戏数据地图 v1.md`（player/pet/equipment/... 表结构 + 纯机制说明，调数值只改 config）
- `策划必须阅读！.txt`（策划约束）
- `Mvp/` 现有代码（尤其是 `config.js`、`market_bot.js`、`supabase/migrate_*.sql`）

约定：**数据新增先写进 `游戏数据地图 v1.md`，再写代码；纯机制（合成变异/涅槃/进化/市场冷启动）只动 `config.js`，不新增表字段。**

## 3. 各 Agent 职责与交接物

### 3.1 策划 / 数值 Agent（DeepSeek）
- 输入：设计文档、玩家反馈、当前待办（设计文档 §12）
- 输出：需求清单、数值表（成长系数、变异概率、掉率、交易税等，落到 `config.js` 段）、更新后的数据地图
- 边界：严格守住 §9「不做」清单（不做 ARPG / 天赋树 / 技能 / 剧情 / 公会 / 赛季 / 付费）

### 3.2 系统架构 Agent（DeepSeek）
- 输出：模块依赖图、DB schema 变更、RPC / 函数契约、`config.js` 结构草案
- 关键：怪物等级段系统（§6）、区域系统（§7 待做）的 schema 设计

### 3.3 后端 Agent（GPT）
- 输出：`supabase/migrate_*.sql`、security definer 函数（如 `bot_buy_equip`）、索引
- 接收：架构 Agent 的契约 + 策划的数值

### 3.4 前端 Agent（GPT）
- 输出：`Mvp/` 下的 JS 模块（战斗、背包、市场、宠物）
- 接收：架构 Agent 的接口 + 策划的体验要求（§10 美术：暗黑、无 emoji、无粒子、飘字反馈）

### 3.5 测试 / 自测 Agent（GPT）
- 输出：删档自测脚本 / 清单、关键链路回归（挂机→掉宝→鉴定→交易→合成/涅槃）

## 4. 协作工作流（串行 + 并行）

```
策划(DeepSeek) ──需求/数值──▶ 架构(DeepSeek) ──契约──┬─▶ 后端(GPT) ─┐
                                                       └─▶ 前端(GPT) ─┤
                                                                     ├─▶ 测试(GPT) ──▶ 回灌策划
```
- 策划先出需求与数值，作为一切基线；
- 架构据此定结构，后端 / 前端**并行**开发；
- 测试跑完后，发现的问题回灌策划，进入下一轮迭代。

---

## 5. 在 CodeBuddy 中落地（步骤）

1. 在「智能工作流 / 高级功能」创建 5 个**自定义 Agent**，每个填入上面的职责与「必读文件」清单作为系统指令。
2. 模型接入与绑定：
   - **GPT-5.6（写码用）**：走中转站，需在「自定义模型（API 接入）」里新增一个模型，填入你 relay 的 `base_url` + `api_key`（项目根目录的 `relay-selfcheck.sh/.log/.out` 就是这套中继的自检脚本，可据此确认 relay 可用后再接入）。接入后，后端/前端/测试三个 Agent 绑定这个自定义 GPT-5.6。
   - **DeepSeek（策划/架构用）**：若也走中转站，同样以自定义模型方式接入；若 CodeBuddy 内置有 DeepSeek 也可直接选。
3. 触发顺序按 §4 工作流串联；共享上下文靠上述 3 个文档 + `Mvp/` 代码。
4. 每轮产物提交前，由架构 Agent 做一次接口一致性校验。

> ⚠️ **待你在 UI 实测确认的一点**：CodeBuddy 自定义 Agent 是否支持「逐 Agent 绑定不同模型」。
> 文档站是 SPA，我无法读到正文。若**不支持**逐 Agent 绑模型，备选方案：
> (a) 按工作流阶段手动切换全局模型（策划阶段选 DeepSeek，写码阶段切 GPT）；
> (b) 把 DeepSeek 当作外部 API，在策划 Agent 的指令里调用，写码 Agent 仍走 GPT。

## 7. 风险与待确认

1. **GPT 具体版本**：已确认 = **GPT-5.6，通过中转站（relay）接入**。需在 CodeBuddy「自定义模型（API 接入）」配置 relay 的 base_url + key（参考项目根 `relay-selfcheck.*`）。
2. **逐 Agent 绑模型**：是否原生支持，需在 CodeBuddy UI 验证（见 §5 备注）。
3. **上下文传递**：多个 Agent 之间靠文件交接，建议固定「设计文档 + 数据地图 + config.js」为单一事实源，避免漂移。
4. **模型可获取性**：DeepSeek 与 GPT 都需在 CodeBuddy 模型列表/自定义 API 中可用并已配置密钥。
